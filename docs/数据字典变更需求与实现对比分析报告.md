# 数据字典变更需求与实现对比分析报告

## 一、完整需求文档

### 1.1 原始需求
- 系统中有业务数据字典表 `biz_ddct_item`、`biz_ddct_type`，需要日常团队不同的人进行变更，变更涉及增删改
- 需求是让开发填写变更表，之后提交存一个记录，**不是流程记录，是变更记录**
- **审批人员能看见原始的与要变更的，在同一个页面，方便审核**
- 前端页面如何设计举例说明，后端逻辑怎么设计，包含哪些API，以及数据库表有哪些，怎么设计
- 变更表应该有哪些字段，主要变更的字段为 `biz_ddct_item` 中的：
  - `DCT_SEQ`（排序号）
  - `DCT_GRP`（字典组）
  - `DCT_KEY`（字典键）
  - `DCT_VAL_NM`（字典值名称）
  - `DCT_TP_NM`（字典类型名称）
  - `DCT_VAL`（字典值）
  - `DCT_TP`（字典类型）
  - `DCT_DSC`（字典描述）
- 提供原始字典表

### 1.2 功能需求

#### 1.2.1 用户角色
| 角色 | 职责 | 权限 |
|------|------|------|
| 开发人员 | 提交字典变更申请 | 提交申请、查看历史 |
| 审批人员 | 审批变更申请 | 审批操作、查看所有记录 |
| 系统管理员 | 执行变更、系统维护 | 所有权限 |
| 普通用户 | 使用字典数据 | 只读权限 |

#### 1.2.2 功能需求
1. **变更申请功能**
   - 支持新增、修改、删除字典类型
   - 支持草稿保存
   - 修改类型时，需要加载现有数据（字典类型信息和字典项）

2. **审批功能**
   - **可视化变更对比（原始值 vs 变更值）** - **核心需求**
   - 审批人员能在同一个页面看到原始值与变更值
   - 支持通过/拒绝审批
   - 填写审批意见

3. **变更执行功能**
   - 手动执行变更
   - 事务性保证
   - 失败回滚机制

4. **变更记录查询功能**
   - 支持多条件查询
   - 支持分页
   - 支持查看详情

### 1.3 业务流程

#### 1.3.1 变更申请流程
1. 选择变更类型（新增/修改/删除）
2. 如果是修改/删除，选择现有字典类型
3. 如果是修改，加载现有字典类型和字典项数据
4. 填写/修改字典类型信息
5. 管理字典项（新增/修改/删除字典项）
6. 填写变更原因和变更影响
7. 保存草稿或提交申请

#### 1.3.2 审批流程
1. 查看待审批列表
2. 查看变更详情
3. **在同一个页面看到原始值与变更值的对比**
4. 分析变更影响
5. 填写审批意见
6. 通过或拒绝

#### 1.3.3 变更执行流程
1. 查看待执行列表
2. 执行变更
3. 更新执行状态
4. 记录执行结果

### 1.4 数据需求

#### 1.4.1 数据库表设计
1. **字典类型变更主表（biz_ddct_type_change）**
   - 存储字典类型的变更记录
   - 包含变更类型、原始值、新值、审批状态、执行状态等

2. **字典项变更明细表（biz_ddct_item_change）**
   - 存储字典项的变更记录
   - 包含操作类型、原始值、新值、执行状态等

## 三、需求与实现不符合的地方

### 3.1 核心功能缺失

#### 3.1.1 修改字典类型时加载现有数据功能缺失 ⚠️ **严重**
**需求：**
- 修改字典类型时，需要选择现有字典类型，并自动加载该字典类型的所有信息（包括字典类型信息和所有字典项）

**当前实现：**
- 前端只提供了手动输入字典类型ID的输入框
- 没有字典类型下拉选择功能
- 没有根据字典类型ID加载数据的API调用
- 后端没有提供加载字典类型和字典项数据的接口

**影响：**
- 用户体验差，需要手动输入ID
- 容易出错，ID可能输入错误
- 无法自动填充原始值，用户需要手动输入所有原始值和新值

#### 3.1.2 审批页面变更对比展示不完整 ⚠️ **严重**
**需求：**
- 审批人员能在同一个页面看到原始值与变更值的对比
- 需要方便审核的可视化对比效果

**当前实现：**
- 字典类型变更：只以文本形式展示了原值和新值，没有并排对比
- 字典项变更：以表格形式展示，原值和新值在不同列，但没有高亮差异
- 缺少明显的对比视觉效果

**影响：**
- 审批人员需要仔细对比才能发现变更内容
- 不符合需求中"方便审核"的要求

#### 3.1.3 变更执行功能未实现 ⚠️ **严重**
**需求：**
- 执行变更时，需要真正对 `biz_ddct_type` 和 `biz_ddct_item` 表进行增删改操作

**当前实现：**
- `executeDictTypeChange` 和 `executeDictItemChange` 方法只有日志输出，没有实际数据库操作
- 没有真正执行变更逻辑

**影响：**
- 审批通过的变更无法真正应用到系统中
- 系统功能不完整

### 3.2 功能不完善

#### 3.2.1 删除字典类型时缺少数据加载功能
**需求：**
- 删除字典类型时，应该先加载该字典类型的信息，让用户确认

**当前实现：**
- 只提供了手动输入字典类型ID的输入框
- 没有加载和展示字典类型信息的功能

#### 3.2.2 字典项修改时缺少原始数据加载功能
**需求：**
- 修改字典项时，应该能够选择现有字典项，并自动加载原始数据

**当前实现：**
- 用户需要手动输入所有字段，包括原始值和新值
- 没有选择现有字典项的功能

#### 3.2.3 前端数据提交格式问题
**问题：**
- 前端提交的数据结构中，字典项变更的 `oldData` 字段在修改操作时可能为空
- 后端没有自动加载和填充 `oldData` 的逻辑

### 3.3 用户体验问题

#### 3.3.1 字典类型选择方式不友好
- 当前使用手动输入ID的方式，应该改为下拉选择
- 应该提供字典类型列表查询接口

#### 3.3.2 变更对比展示不够直观
- 应该使用并排对比或差异高亮的方式展示变更内容
- 可以使用颜色标记新增、修改、删除的内容

#### 3.3.3 缺少数据验证和提示
- 修改操作时，如果字典类型ID不存在，应该有明确的错误提示
- 字典项修改时，如果字典项不存在，应该有明确的错误提示

但是存在以下关键问题：
- ❌ **修改字典类型时加载现有数据功能缺失**（严重）

### 5.2 优先级建议
1. **高优先级（必须修复）**
